# Incident: recon failure — core.orders source drift (job run 1022907919431904)

- **Date:** 2026-09-18 (job started 15:53:06 UTC; `notify_devin` fired the recon-failure webhook)
- **Job:** `redshift-migration-nightly-recon` (id 220238957207364), run 1022907919431904
- **Failing task:** `recon_check` (task run 966249847901455) — `raise_error`:
  `RECONCILIATION FAILED: ROW COUNT MISMATCH core.orders: redshift=65197 databricks=64797; AGGREGATE MISMATCH orders revenue/max_ts: redshift=57149040.89|2026-09-18 15:44:37 databricks=57046463.48|2026-09-18 15:33:49`
- **Run branch:** `migration-run-10`. Converted ETL used for the mart rebuild comes from the open
  conversion PR #33 (`databricks/etl/10_build_daily_revenue.sql`, `11_build_customer_ltv.sql`).

## Root cause

Source-side freshness drift, not a conversion bug. A second batch of 400 orders today
(`order_id` 64798–65197, one distinct `loaded_at` = 2026-09-18 15:52:49 UTC, `order_ts`
back-dated across 2026-09-17 15:53:37 → 2026-09-18 15:44:37, all status `PLACED`) landed in live
Redshift `core.orders` **17 seconds** before the recon job started. `migration_demo.core.orders`
was last written at 15:40:24 UTC (Delta version 1, the 400-row append from the earlier incident,
run 806972366269710), so the target was a point-in-time copy the source had moved past again.

Evidence (queried on warehouse 565cd2fd713738c4 through `redshift_src`, and cross-checked
directly on Redshift via the Data API):

- Anti-join on `order_id`: exactly **400** rows in Redshift and missing in Databricks;
  **0** rows in Databricks and missing in Redshift.
- Sum of the 400 missing rows' `order_total` = **102577.41** = 57149040.89 − 57046463.48 (the
  aggregate gap is fully explained by the missing rows); their `MAX(order_ts)` = 2026-09-18
  15:44:37 = the source-side max in the failure message.
- **0** common rows differ on any column (`customer_id`, `order_ts`, `order_status`,
  `order_total`, `sales_channel`) — pure appends, no updates or deletes.
- Direct Redshift Data API check: `COUNT(*)=65197`, `SUM(order_total)=57149040.89`,
  `MAX(loaded_at)=2026-09-18 15:52:49`; `loaded_at` on 2026-09-18 has exactly two values,
  15:35:50 (400 rows, previous incident) and 15:52:49 (400 rows, this incident).
- `core.customers` (2000/2000) and `core.order_items` (151803/151803) unaffected; no
  `order_items` exist for the 400 new orders on either side.
- Marts were equal on both sides before remediation (2989/2989 and 2000/2000 rows,
  `avg_mismatch_rows` = 0, all four `EXCEPT` diffs 0; both `mart.daily_revenue` at max
  `order_date` 2026-09-17) because the Redshift nightly mart refresh had not run since the batch
  either. This rules out the converted ETL/report SQL (PR #33) as a cause.

## Remediation (data catch-up only — no code changes)

1. Caught the target up through federation, idempotently (schema preserved, only missing keys):
   `INSERT INTO migration_demo.core.orders SELECT s.* FROM redshift_src.core.orders s LEFT ANTI JOIN migration_demo.core.orders t ON s.order_id = t.order_id`
   → `num_inserted_rows = 400`.
2. Refreshed Redshift marts as `demoadmin` by running the customer's unchanged nightly ETL
   (`sql/etl/10_build_daily_revenue.sql`, `sql/etl/11_build_customer_ltv.sql`), then
   `GRANT SELECT ON ALL TABLES IN SCHEMA mart TO PUBLIC` (DROP + CTAS loses grants; the
   federation user needs SELECT). Nothing under `sql/` was modified; `core.*` was not touched.
3. Rebuilt Databricks marts with the converted ETL from PR #33, unchanged.

Mart row counts did not change this time (`mart.daily_revenue` stayed at 2989, `mart.customer_ltv`
at 2000): the back-dated 2026-09-17 orders fell into region × channel_group cells that already
existed, so only the metric values moved (e.g. 2026-09-17 `order_count` is now 273 on both sides).
2026-09-18 orders are excluded by `order_ts < current_date`.

## Follow-up

Third occurrence of this failure class (after runs 40206984702513 on 2026-09-03 and
806972366269710 earlier today). The target is a point-in-time copy, so every source append
re-triggers the alert until either a scheduled catch-up (the anti-join insert above, or a `MERGE`
on `order_id`) runs before the recon, or the recon is re-scoped to a cutoff. The converted
`mart-refresh-nightly` job (`databricks/jobs/refresh_marts.job.yml`, PR #33) is still not deployed
to the workspace; when it is, it should be preceded by the same core-table catch-up so both sides
refresh from the same source snapshot. This is a decision for the migration owners, not made here.
