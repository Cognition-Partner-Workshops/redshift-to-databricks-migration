# Incident: nightly recon failure — core.orders drift (job run 1000343466204228)

- **Date:** 2026-09-02 (job started 05:03:04 UTC; recon-failure webhook fired via `notify_devin`)
- **Job:** `redshift-migration-nightly-recon` (id 220238957207364), run 1000343466204228
- **Failing task:** `recon_check` (task run 809871931900456) — `raise_error`:
  `RECONCILIATION FAILED: ROW COUNT MISMATCH core.orders: redshift=63597 databricks=63197; AGGREGATE MISMATCH orders revenue/max_ts: redshift=56734168.36|2026-09-02 04:58:49 databricks=56636917.82|2026-08-20 04:47:04`

## Root cause

Source-side freshness drift, not a conversion bug. A single batch of 400 orders
(`order_id` 63198–63597, all `loaded_at` = 2026-09-02 05:02:50 UTC, `order_ts` back-dated
across 2026-09-01 05:02:49 → 2026-09-02 04:58:49, all status `PLACED`) landed in live Redshift
`core.orders` 14 seconds before the recon job started. `migration_demo.core.orders` had last
been synced on 2026-08-20 (target max `order_ts` 2026-08-20 04:47:04), so the target was behind.

Evidence (all queried on warehouse 565cd2fd713738c4 through `redshift_src`, and cross-checked
directly on Redshift as `demoadmin` via psql):

- `LEFT ANTI JOIN` on `order_id`: exactly **400** rows in Redshift and missing in Databricks;
  **0** rows in Databricks and missing in Redshift.
- Sum of the 400 missing rows' `order_total` = **97250.54** = 56734168.36 − 56636917.82 (the
  aggregate gap is fully explained by the missing rows).
- **0** common rows differ on any column (`customer_id`, `order_ts`, `order_status`,
  `order_total`, `sales_channel`), i.e. no updates/deletes, pure appends.
- `core.customers` (2000/2000) and `core.order_items` (151803/151803) unaffected; no
  `order_items` exist for the 400 new orders on either side.
- Marts were equal on both sides before remediation (row counts, `avg_mismatch_rows`=0, all
  four `EXCEPT` diffs 0) because the Redshift nightly mart refresh had not run since the drift
  either (Redshift `mart.daily_revenue` max `order_date` was still 2026-08-20). This rules out
  the converted ETL/report SQL as a cause.

## Remediation (data catch-up only — no code changes)

1. Caught the target up through federation, idempotently (schema preserved, only missing keys):
   `INSERT INTO migration_demo.core.orders SELECT s.* FROM redshift_src.core.orders s LEFT ANTI JOIN migration_demo.core.orders t ON s.order_id = t.order_id`
   → 400 rows inserted.
2. Refreshed Redshift marts as `demoadmin` by running the customer's unchanged nightly ETL
   (`sql/etl/10_build_daily_revenue.sql`, `sql/etl/11_build_customer_ltv.sql`), then
   `GRANT SELECT ON ALL TABLES IN SCHEMA mart TO PUBLIC` (drop+CTAS loses grants; the
   federation user needs SELECT). Legacy SQL under `sql/` was not modified.
3. Rebuilt Databricks marts with the converted ETL from PR #20
   (`databricks/etl/10_build_daily_revenue.sql`, `databricks/etl/11_build_customer_ltv.sql`), unchanged.

## Follow-up

The target is a point-in-time copy; every source append will re-trigger this incident until a
scheduled catch-up (the anti-join insert above, or a `MERGE` on `order_id`) runs before the
06:00 UTC recon, or the recon is re-scoped to a cutoff. This is a decision for the migration
owners, not made here.
