# Warehouse Analytics — Redshift → Databricks

SQL estate for our order-analytics warehouse. The original Amazon Redshift
Serverless implementation (workgroup `demo-wg`, database `demo`, us-east-1)
lives under `sql/` for reference; the Databricks-native implementation lives
under `databricks/` and is the target going forward.

## Databricks target layout

Everything is in Unity Catalog under the `migration_demo` catalog, organised as
a medallion (bronze → silver → gold → reports):

| Layer  | Schema                  | Objects                                  | Source file(s) |
|--------|-------------------------|------------------------------------------|----------------|
| Bronze | `migration_demo.core`   | `customers`, `orders`, `order_items` (Delta, append-only copies of the Redshift core tables) | `databricks/ddl/02_core_tables.sql` |
| Silver | `migration_demo.silver` | `enriched_orders` table, `avg_order_value()` function | `databricks/ddl/03_silver_tables.sql`, `databricks/ddl/04_functions.sql`, `databricks/silver/05_load_enriched_orders.sql` |
| Gold   | `migration_demo.mart`   | `daily_revenue`, `customer_ltv`          | `databricks/etl/10_build_daily_revenue.sql`, `databricks/etl/11_build_customer_ltv.sql` |
| Reports| (read gold)             | region topline, 30-day channel trend     | `databricks/reports/20_region_topline.sql`, `databricks/reports/21_channel_trend.sql` |

Orchestration is a Databricks Asset Bundle (`databricks.yml`) with one Lakeflow
Job, `databricks/jobs/refresh_marts.job.yml`.

```
databricks/
  ddl/      01_schemas, 02_core_tables, 03_silver_tables, 04_functions
  silver/   05_load_enriched_orders   (incremental INSERT, idempotent)
  etl/      10_build_daily_revenue, 11_build_customer_ltv   (CREATE OR REPLACE TABLE)
  jobs/     refresh_marts.job.yml     (replaces mart.sp_refresh_marts)
  reports/  20_region_topline, 21_channel_trend
```

### DDL translation

- `core` and `mart` schemas keep their names (so the recon harness and BI only
  need a catalog prefix); a new `silver` schema is added.
- Tables are Delta. `DISTSTYLE`/`DISTKEY` are dropped; each former `SORTKEY`
  becomes `CLUSTER BY` (liquid clustering).
- `IDENTITY(1,1)` → `BIGINT GENERATED BY DEFAULT AS IDENTITY`. Identity columns
  must be `BIGINT`, so `customer_id` widens from `INTEGER` to `BIGINT`
  everywhere. `BY DEFAULT` lets the backfill insert the Redshift ids as-is.
- `CHAR(n)` → `STRING`. Strings are no longer blank padded, so status
  comparisons use `trim()`.
- `GETDATE()` defaults → `current_timestamp()`.
- Primary/foreign keys are declared as informational constraints.

### Consolidated silver layer

Both Redshift marts repeated the same `core.orders ⋈ core.customers` join and
the same cancelled-order filter (written fragilely as `<> 'CANCELLED  '` to
match the `CHAR(10)` padding). `silver.enriched_orders` does this once:

- join to `customers` for `customer_code`, `region`;
- keep only valid orders: `trim(order_status) <> 'CANCELLED'`;
- precompute `order_date = to_date(order_ts)` (Redshift `TRUNC(order_ts)`) and
  `channel_group` (`CASE WHEN sales_channel IN ('web','app') THEN 'ONLINE' ELSE 'RETAIL'`,
  formerly `DECODE`).

Because `core.orders` is append-only and `order_id` is a monotonically
increasing identity, the load is a plain incremental `INSERT ... WHERE
order_id > MAX(order_id) already in silver`. Re-running it inserts 0 rows.
The two gold marts read only `silver.enriched_orders`, so any change to the
valid-order rule is made in exactly one place.

### Canonical `avg_order_value`

Redshift defined the metric two different ways:

| Mart            | Redshift formula                                   |
|-----------------|----------------------------------------------------|
| `daily_revenue` | `SUM(order_total) / NULLIF(COUNT(DISTINCT order_id), 0)` → `DECIMAL(38,4)` |
| `customer_ltv`  | `AVG(order_total)` → `DECIMAL(38,2)`               |

Within a group these are the same quantity — gross revenue of valid orders
divided by the number of valid orders (`order_id` is unique, so `COUNT(DISTINCT
order_id)` = `COUNT(*)`, and `AVG` = `SUM / COUNT`). The canonical definition
is therefore:

> **avg_order_value = SUM(order_total) / COUNT(order_id) over valid
> (non-cancelled) orders, NULL when there are no orders, truncated toward
> zero at the mart's published scale.**

It is implemented once as `migration_demo.silver.avg_order_value(gross_revenue,
order_count, scale)`. `daily_revenue` calls it with `scale = 4` and
`customer_ltv` with `scale = 2`, matching the column types Redshift produced.
Truncation (not rounding) is deliberate: Redshift decimal division truncates,
and keeping that behaviour is what lets the marts reconcile row-for-row.

### Full refresh → Databricks-native

`DROP TABLE` + `CREATE TABLE AS` is replaced by:

- silver: incremental `INSERT` (above), so the expensive join runs only over
  new orders;
- gold: `CREATE OR REPLACE TABLE ... AS SELECT` over silver. This is a single
  atomic Delta commit, so readers never see a missing table, and the previous
  version stays available through time travel.

### Orchestration

`mart.sp_refresh_marts()` (plpgsql) only logged and dropped a stage table; the
real `10_* → 11_*` ordering lived in the scheduler's file names. The Lakeflow
Job `order-analytics-refresh-marts` makes the order an explicit task DAG:

```
load_enriched_orders  ──┬──▶ build_daily_revenue
                        └──▶ build_customer_ltv
```

Each task is a SQL-file task on the serverless SQL warehouse
(`565cd2fd713738c4`). It runs nightly at 02:00 UTC, before the 06:00 UTC recon
job, with `max_concurrent_runs: 1`.

```
databricks bundle validate
databricks bundle deploy -t dev
databricks bundle run refresh_marts -t dev
```

### Reports

- `20_region_topline`: reads `migration_demo.mart.customer_ltv`; the regional
  AOV uses the same truncating `avg_order_value()` function so it matches
  Redshift's `AVG` over `DECIMAL(38,2)`.
- `21_channel_trend`: reads `migration_demo.mart.daily_revenue`;
  `DATEADD(day, -30, TRUNC(GETDATE()))` → `date_sub(current_date(), 30)`.

### Reconciliation

Marts built with this code were compared against `redshift_src.mart.*` (the
Redshift marts via Lakehouse Federation): `customer_ltv` matched all 2,000 rows
including `avg_order_value`; `daily_revenue` matched all 2,989 common rows on
every metric, plus extra rows for the day that completed after the last
Redshift refresh. See `.agents/skills/testing-recon-suite/SKILL.md` for the
recon procedure.

## Redshift (reference)

- `sql/ddl/` — table definitions (core order/customer tables)
- `sql/etl/` — nightly mart builds, run in numeric order by the scheduler
  (`10_*` → `11_*`), plus the `mart.sp_refresh_marts` wrapper procedure
- `sql/reports/` — BI report queries consumed by the exec dashboard

Redshift conventions: marts rebuilt nightly by full refresh (DROP + CTAS);
`core.*` tables are append-only; distribution/sort keys tuned for the current
query mix.
